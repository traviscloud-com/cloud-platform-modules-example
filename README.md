# cloud-platform-modules-example

> **Example repository.** This is a sanitized public copy of a pattern that runs in a private
> setup. Every hostname, organisation, tenant, subscription, client ID, vault, registry and
> storage name is a placeholder (`example.com`, `demo`, `your-org`, all-zero GUIDs); nothing here
> points at a real deployment, and it contains no secrets. Where the text says a repo is private,
> that describes the original setup. Companion repos:
> [manifests](https://github.com/traviscloud-com/cloud-platform-manifests-example),
> [infra](https://github.com/traviscloud-com/cloud-platform-infra-example),
> [catalog](https://github.com/traviscloud-com/cloud-platform-catalog-example),
> [modules](https://github.com/traviscloud-com/cloud-platform-modules-example),
> [ouroboros](https://github.com/traviscloud-com/ouroboros-example).

Plain Terraform modules (no Terragrunt inside) extracted from
`cloud-platform-infra-example`. Each module is versioned and tagged independently.

## Modules

| Module | Description |
| --- | --- |
| `local-cluster` | Per-environment resources for a local (rancher-desktop) cluster: resource group, Key Vault, External Secrets service principal, optional container registry (ACR) and optional blob storage. Composes `service-principal`, `key-vault` and `github-actions-identity`. |
| `service-principal` | Entra ID application + service principal with a Terraform-rotated client secret. |
| `key-vault` | Azure Key Vault (AVM-based) with RBAC access. |
| `github-actions-identity` | Entra ID identity with federated (OIDC) credentials for GitHub Actions. |

See each module's `README.md` for inputs and outputs.

## Layout

```
modules/<name>/{main.tf,variables.tf,outputs.tf,versions.tf,README.md}
modules/<name>/examples/basic/
modules/<name>/tests/
```

## Versioning and tags

Every module is tagged on its own as `<module>/vX.Y.Z` (for example
`key-vault/v1.0.0`). Tags are created by the `release` workflow
(Actions -> release -> Run workflow, inputs `module` and `version`), which
tags the current `main` commit and creates a GitHub release.

## Consuming a module

Pin to a module tag:

```hcl
module "key_vault" {
  source = "git::https://github.com/traviscloud-com/cloud-platform-modules-example.git//modules/key-vault?ref=key-vault/v1.0.0"
  # ...
}
```

`local-cluster` calls its siblings through relative sources
(`../service-principal`, `../key-vault`, `../github-actions-identity`), so consumers MUST use the
double-slash form `//modules/local-cluster` so the whole repo is fetched and
the relative paths resolve:

```hcl
source = "git::https://github.com/traviscloud-com/cloud-platform-modules-example.git//modules/local-cluster?ref=local-cluster/v1.1.0"
```

Note that the siblings resolve from the same checkout, i.e. at the
`local-cluster` tag, not at their own tags.

## Running checks locally

Terraform is pinned in `.tool-versions` (same as CI). The other CLI tools
(gitleaks, tflint, trivy, terraform-docs) are pinned and sha256-verified in
`scripts/install-tools.sh`, which installs them into `~/.local/bin`:

```bash
scripts/install-tools.sh          # or name tools: scripts/install-tools.sh trivy

scripts/lint.sh                   # tflint + trivy config scan + docs-check
scripts/lint.sh tflint            # | trivy | docs (regenerate READMEs) | docs-check
```

Module READMEs are generated by terraform-docs (`.terraform-docs.yml`); run
`scripts/lint.sh docs` after changing variables/outputs and commit the result
(CI fails on stale READMEs). `terraform fmt`, `validate` and `test` run per
module:

```bash
terraform fmt -check -recursive

m=key-vault   # any directory under modules/
terraform -chdir=modules/$m init -backend=false
terraform -chdir=modules/$m validate
terraform -chdir=modules/$m test   # only for modules that have a tests/ directory
```

Enable the secret-scanning git hooks once per clone (`pre-commit` scans staged
changes, `pre-push` scans the working tree and full history with gitleaks):

```bash
git config core.hooksPath githooks
```

## Security

This is the public example copy: names and identifiers are placeholders.
Secrets and credentials are never committed: client secrets, state
files, `.env` and `*.tfvars` (only `*.example.tfvars`) are gitignored and
blocked by the hooks, and gitleaks runs in CI (`gitleaks.yml`, plus a weekly
full-history sweep) and in the pre-commit hook.

- Tool versions are pinned: Terraform in `.tool-versions` and CI; gitleaks,
  tflint, trivy and terraform-docs in `scripts/install-tools.sh`, which verifies
  their sha256 checksums. Third-party GitHub Actions are pinned by full commit SHA.
- Module sources (AVM) are pinned by commit SHA.
- HIGH/CRITICAL `trivy config` findings fail CI; accepted exceptions live in
  `.trivyignore`, each with a justification.
- Workflows run with least-privilege `GITHUB_TOKEN` permissions; only the
  release job gets `contents: write`.
